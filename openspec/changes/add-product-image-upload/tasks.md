Found and fixed a real bug along the way: `ProductImage.data` mapped `@Lob byte[]` to Postgres's legacy Large Object (`oid`) API, which threw `HibernateException: Unable to access lob stream` outside the write transaction — removed `@Lob` so it maps to a plain `bytea` column (Hibernate 6/7 default), fixing upload and serve both. Also found the umlaut-filename test itself was broken, not the product: RestAssured's `.multiPart(name, filename, bytes, mime)` mis-encodes non-ASCII filenames client-side — diagnosed by sending a hand-built multipart body with genuine UTF-8 bytes, which the server decoded correctly, proving the app code was already right; fixed the test to build the request by hand instead.

**Bugs found + fixed during browser verification:**
1. Internal image references (`ProductImageDto.url`, `Product.imageUrl`, the `INTERNAL_IMAGE_URL` regex, `image-chooser.js`'s prefix check, `product-images.js`'s `INTERNAL_PREFIX`) all used `/api/product-images/{id}` — the real REST path. But every frontend fetch helper (`apiFetch`/`apiFetchForm`/`apiFetchBlob`, `lib/api.js`) prepends `API_BASE` which already ends in `/api` (matching the existing convention: `apiFetch("/company/products")`, never `apiFetch("/api/company/products")`). Result: every internal-image request hit `/api/api/product-images/{id}` → 404, caught silently by `load()`'s try/catch, leaving the product list empty. Fixed by dropping the `/api` prefix from the *stored/returned reference* everywhere above (`/product-images/{id}`) — the actual backend `@Path` is unchanged, this was purely about what string value the frontend uses as its internal-reference convention.
2. Pre-existing, app-wide bug in `lib/api.js` (not introduced by this change, just newly surfaced by it): `handleResponse`/`apiFetchBlob`/`apiDownload` all used `response.text()` directly as the error message, but the backend's `ApiExceptionMapper`/`ValidationExceptionMapper` return JSON (`{"message": "..."}`) — every rejected-upload (and, in principle, every other app error) toast was showing the raw JSON blob instead of the German text. Fixed with one shared `extractErrorMessage()` that JSON-parses the body and falls back to raw text for non-JSON error responses (e.g. a proxy error page). Flagged to Chris as a cross-cutting fix beyond this change's nominal scope, but small, safe, and directly required by this change's own "shows a German error" acceptance criterion.

Also caught (not a bug, environment-only): the browser was serving stale cached JS after edits — worked around via the project's documented `127.0.0.1` vs `localhost` origin-switch trick (both already CORS-whitelisted) rather than `about:blank` alone, which wasn't sufficient this time.
